Secure agent design with small local models.

Histora Health builds clinical record software. Running a model inside the customer's perimeter changes the objective: the priority is not the model's knowledge but the ability to guarantee that the actions it emits are safe and executable.

The empirical work behind that, and the architecture it produced, gets published here with the benchmarks and the raw data.

What can be guaranteed about the actions a small local model emits?

Four layers between what an agent proposes and what executes: an option surface computed from live state, so a signed record leaves the choices the moment it is signed; order forced at the system level, which is the one class of rule a JSON Schema structurally cannot state; verification that the action names the record the request named; and a person who confirms.

Procedure coding from dictation runs end to end. Two of the demonstrations need no model at all, because what they show is a property of a compiled artefact rather than a statistic over samples.

Limits of the standard control mechanisms

Prompting and trust is not viable. Small models have a high rate of malformed or unexecutable output on a text protocol — fourteen malformed outputs in thirty turns, and none of ten legitimate tasks completed. Before asking whether the model respects a rule, you have to ask whether it emits anything executable.

Post-hoc validation is sound; the retry is the cost. With enums regenerated each turn from live state, calls naming a forbidden record are rejected and the error returned to the model. Writes reaching the closed record: zero, in every arm measured. What fails is the correction — small models correct their own output badly after a rejection, so throughput comes to depend on retries that do not converge.

Constrained decoding makes the model usable, and introduces a failure of its own. Restricting the generated tokens took the same model from none of ten legitimate tasks to all ten. It also produced the substitution below, which is why enforcement now sits at the decision point rather than at the sampler.

Procedure coding from dictation, measured against gates decided in advance: coverage 0.8, zero proposals against a tooth the dictation did not name, no attention needed beyond a confirmation, median latency 3.5 seconds. Four of twenty carry the wrong code — legal for the surface, wrong for the procedure — which is the same failure one level down and the open problem.

The critical failure: silent substitution

Constrained decoding forces the model to always choose a valid option. When a user asks it to modify a record that is blocked — and therefore absent from the mask of legal options — the model has no way to stop. Instead of declining, it keeps the intent, substitutes the forbidden target for a valid one, and executes the action on the wrong record.

The failure is silent and undetectable by JSON schemas and classical validators: the generated action is technically legal, every argument belongs to the permitted vocabulary, and no violation is logged because nothing was violated.

The trigger is not adversarial pressure. An explicit fabricated administrative override produced zero substitutions in twenty attempts; a phrasing that reads as ordinary filing produced five out of five. Independent work on frontier models found the same shape, and four attempts to detect it from the model's internal state returned null on a rig whose positive control passes.

The architecture this requires

Four layers, none of which depends on the model's intelligence to avoid the error.

An option surface derived from state. Tools and argument enums are not fixed schemas — they are regenerated each turn from the live state of the system, so a signed record disappears from the possible values the moment it is signed.

Order forced at the system level. Clinical process rules — pick tooth, pick surface, audit, sign — compile into tool availability, so incorrect sequences are unreachable from the orchestrator rather than rejected after the fact. This is the class of rule a JSON Schema structurally cannot state: only after that is not an assertion about shape.

Reference verification before executing. A strict algorithmic check requiring string overlap between the argument the model selected and the entities named explicitly in the original prompt. If the model acts on a record the user did not name, it is blocked. It reports rather than corrects — a guard that corrected silently would be making clinical decisions by string similarity.

Propose-and-confirm. Because no autonomous system can guarantee correctness against substitution, the agent structures and proposes the change only. A person sees the target record in the interface and confirms execution.

What comes next

Permission constraints produced every result above, and they are the least favourable case: the task is choosing between interchangeable entities, so a blocked request always has a neighbour to land on.

Structural constraints invert that. The clinician asks for anatomically valid things, so the model is kept inside a vocabulary rather than denied something, and silent substitution largely does not arise. It is also where enumeration earns its keep — a hallucinated procedure code is a rejected claim — and where forced order does: pick the tooth, then only that tooth's surfaces, then only the codes valid for that surface. Named and not built.
